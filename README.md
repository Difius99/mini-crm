# Мини-CRM «Объекты и задачи»

Небольшая CRM для строительной компании: постановщик заводит объекты (стройки) и задачи по ним, исполнители берут задачи в работу и отправляют на проверку.

**Стек:** React 19 + TypeScript + Vite, styled-components, react-router, react-hook-form, Supabase (Postgres + Auth + RLS).

---

## Быстрый запуск

```bash
npm install
cp .env.example .env.local   # на Windows: copy .env.example .env.local
# вписать VITE_SUPABASE_ANON_KEY (Supabase → Project Settings → API Keys → anon / publishable)
npm run dev                  # http://localhost:5173
```

Сборка: `npm run build` → папка `dist`.

### Настройка Supabase с нуля

1. Создать проект на supabase.com.
2. **Authentication → Sign In / Providers → Email → Allow new users to sign up = OFF** (открытая регистрация отключена).
3. SQL Editor → выполнить `supabase/migrations/20261105000000_init.sql`.
4. Authentication → Users → Add user: `manager@example.com`, `executor1@example.com`, `executor2@example.com` (галочка **Auto Confirm User**). Профили создадутся автоматически триггером.
5. SQL Editor → выполнить `supabase/seed.sql` (роли, имена, 3 объекта, 6 задач во всех статусах с историей).

### Деплой

Vercel / Netlify: импортировать репозиторий, добавить переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`. Для SPA-роутинга уже лежат `vercel.json` и `public/_redirects`.
В Supabase → Authentication → URL Configuration указать адрес приложения.

## Структура

```
supabase/
  migrations/…_init.sql   схема, RLS, триггеры, функция смены статуса
  seed.sql                тестовые данные
src/
  api/                    запросы к Supabase (objects, tasks, profiles), типы, ошибки
  components/ui/          UI-кит: button, input, textarea, dropdown, modal, spinner, statusBadge
  components/layout/      шапка и каркас страниц
  features/auth/          контекст авторизации, вход, защита роутов
  features/objects/       список объектов, карточка объекта, форма объекта
  features/tasks/         карточка задачи, «Мои задачи», действия, история, форма задачи
  constants.ts            палитра, подписи статусов и ролей
  globalStyle.ts          reset + шрифты
```

Глобального стора нет: состояние авторизации — в React Context, данные экранов — через хук `useRequest`.

## Безопасность

Фронтенд обращается к Supabase напрямую, поэтому **все правила доступа находятся в базе**, а не в интерфейсе. Скрытые кнопки — только удобство.

| Требование | Как сделано |
|---|---|
| Права на уровне БД | RLS на всех 4 таблицах; политики в миграции |
| Исполнитель не читает чужие задачи | `tasks_select`: `is_manager() or assignee_id = auth.uid()` |
| Исполнитель видит только «свои» объекты | `objects_select`: объект виден, если на нём есть его задача |
| Исполнитель не меняет задачи | у исполнителя нет UPDATE-политики на `tasks` |
| Переходы проверяются в БД | статус меняется только функцией `change_task_status`; прямой `UPDATE status` блокирует триггер `tasks_guard` |
| Комментарий при возврате обязателен | проверка внутри `change_task_status` |
| История не подделывается | в `task_history` пишут только функции БД; у клиентов нет политик и прав на INSERT/UPDATE/DELETE |
| Нельзя сменить себе роль | у `profiles` нет политик на запись, права на запись отозваны |
| Регистрация отключена | настройка Auth; пользователи создаются вручную |
| Секреты не во фронтенде | во фронтенде только публичный anon-ключ; `.env.local` в `.gitignore`; `service_role` нигде не используется |

**Проверка вручную** (войти исполнителем, открыть консоль браузера; клиент доступен через импорт или DevTools → Network → повторить запрос с токеном):
- `select` чужой задачи → пустой ответ;
- `update tasks set status='accepted'` → 0 строк (нет политики);
- `rpc('change_task_status', {p_to: 'accepted'})` от исполнителя → «Недопустимый переход»;
- `insert` в `task_history` → `permission denied`.

## Для руководителя (без технических деталей)

Система хранит стройки и задачи по ним. Руководитель создаёт задачу и назначает исполнителя. Исполнитель видит только свои задачи и только те объекты, где они у него есть. Он может взять задачу в работу и отправить на проверку. Руководитель принимает работу или возвращает её на доработку, и при возврате обязательно пишет, что исправить. Каждый шаг автоматически записывается в историю: кто, когда и что изменил.

Правила зашиты в саму базу данных, а не только в экран. Поэтому даже человек, который разбирается в программировании и отправляет запросы в обход интерфейса, не сможет:
- увидеть чужие задачи или объекты, где у него нет задач;
- изменить название, описание или исполнителя задачи;
- «перепрыгнуть» статус, например сразу сделать задачу принятой;
- принять свою же работу (это может только руководитель);
- исправить или удалить запись в истории;
- назначить себе роль руководителя.

Зарегистрироваться самостоятельно нельзя: учётные записи создаёт администратор.

## Решения и допущения

- **Роль хранится в `profiles.role`**, назначается администратором через SQL. Пользователь один раз создаётся в Auth, профиль появляется автоматически с ролью «исполнитель».
- **Исполнителем задачи может быть только пользователь с ролью «исполнитель»** (проверяется в БД).
- **Постановщик может редактировать задачу в любом статусе** (название, описание, исполнитель), но статус меняет только по таблице переходов.
- **Удаление объекта удаляет его задачи, удаление задачи — её историю** (каскад). Через API отдельно удалить или изменить историю нельзя.
- **Пользователя, у которого есть задачи или записи в истории, удалить нельзя** (`on delete no action`), чтобы не терять историю. Уволенных сотрудников предполагается блокировать в Auth.
- **Постановщики равноправны**: любой видит и меняет все объекты и задачи.
- **Описание задачи необязательно.**
- Имена всех пользователей видны всем вошедшим (нужно, чтобы показывать исполнителя и автора).

**Что не сделано / можно улучшить:** пагинация и поиск, редактирование профилей и ролей из интерфейса, real-time обновление, автотесты политик (pgTAP), сгенерированные типы Supabase (`supabase gen types`).
